# ADR: Lifecycle Protocol Families and OpenCode Cleanup Blockers

Status: Accepted
Date: 2026-04-23

## Context

The old OpenCode-local `iap-sdlc` and `iap-sdlc-tui` plugins became overloaded. They mixed at least three separate responsibilities:

- OpenCode-native session transport and `/sendoff` UX
- lifecycle/IAP message packet submission
- lifecycle work-item board and transition helpers

This braid made cleanup hard because "IAP" referred to both harness session messaging and lifecycle audit artifacts. Those are not the same system.

The current direction splits the old plugin responsibility into separate canonical homes:

- OpenCode session transport lives in the standalone OpenCode plugin project `/Users/guilhermecastro/Projects/session-inbox`.
- Lifecycle/IAP message semantics live as canonical tools and schemas in `ai-plugins`, centered on `lifecycle-core`.
- Lifecycle work-item behavior lives as canonical lifecycle work-item tools in `ai-plugins`, reusable across SDLC, RLC, MLC, and WLC.

OpenCode root cleanup must not delete the old local plugin sources until these replacement surfaces are live and proven in the harness.

## Decision

There are two immediate filesystem-backed lifecycle protocol families.

### 1. Lifecycle/IAP Messages

Lifecycle/IAP messages are contract-heavy, append-only, auditable packets written under:

```text
.agents/messages/
```

Their implementation model is:

1. Agent calls an agent-specific synthetic tool.
2. The generated wrapper decodes and validates input against the synthetic contract.
3. The wrapper delegates to the canonical tool handler.
4. The canonical handler uses a shared packet writer.
5. The shared packet writer constructs the envelope, generates the canonical filename, writes JSON under `.agents/messages/`, and returns a structured receipt.

The filename is not cosmetic. It is part of the audit protocol. It must be generated by the tool/runtime, not by the agent.

The common packet writer owns:

- timestamp generation
- packet-family/context encoding in the filename
- envelope construction
- `.agents/messages/` persistence
- receipt output

Canonical message tools such as `submit_work`, `submit_review`, `submit_self_assessment`, `submit_review_findings`, and `promote_pattern` should be thin semantic wrappers over this shared implementation.

### 2. Lifecycle Work Items

Lifecycle work items are stateful markdown files that move through lifecycle-specific board folders. They are less contract-heavy than messages, but still need canonical file naming, id policy, board/list/read/create/update/transition/promote behavior, and auditable mutation rules.

Lifecycle roots are lifecycle-method roots, not broad domain roots:

```text
.agents/sdlc/
.agents/rlc/
.agents/mlc/
.agents/wlc/
```

The code convention is:

- `SDLC` = software development lifecycle
- `RLC` = research lifecycle
- `MLC` = marketing lifecycle
- `WLC` = writing lifecycle

This is distinct from broad domain skills or folders named `research`, `marketing`, or `writing`. For example, the `RLC` skill is the research lifecycle method; the `research` skill is broader domain capability.

Lifecycle work-item identifiers should follow the lifecycle/project work-item convention:

```text
<CODE>-<NNN>[subtask]
```

Where:

- `CODE` is a two- or three-character uppercase project/workstream code
- `NNN` is a three-digit sequence
- `subtask` is an optional lowercase letter

Existing examples include shapes like `AP-039b`. The canonical parser should fail closed against this shape unless a work item explicitly records a stronger reason to support legacy ids during migration.

Canonical lifecycle work-item tools mutate by id, not by caller-authored path. Creation generates the markdown filename as:

```text
<CODE>-<NNN>[subtask]-<title-slug>.md
```

For example:

```text
AP-039b-complete-lifecycle-message-synthetic-tool-plumbing.md
```

The id remains the stable dedupe and lookup key. The filename embeds the id for directory readability, but agents should not be responsible for constructing or supplying filenames.

## Synthetic Tool Model

Synthetic tools are not separate business logic. They are generated harness surfaces produced from:

```text
canonical tool implementation
+ trait attachment
+ agent-specific contract override/binding
+ target lowerer
= agent-specific synthetic tool
```

In OpenCode, the generated tool must be visible only to the intended agent through generated agent frontmatter/tool configuration. Sibling agents must not gain global access to another agent's synthetic submission tool.

Traits remain agent capability declarations. They should not become lifecycle-owned or lifecycle-coupled, because lifecycle files relate agents to each other. Coupling traits directly to lifecycle instances would create circularity.

## Skill Boundary

Lifecycle method skills and broad domain skills are different:

- `sdlc`, `rlc`, `mlc`, `wlc` describe orchestration/lifecycle methods.
- `research`, `marketing`, `writing`, and similar skills describe domain capabilities.

The compiler and docs should preserve this distinction. Lifecycle work-item tools should target `.agents/{sdlc,rlc,mlc,wlc}`, not broad domain folders by accident.

## Cleanup Rule

OpenCode cleanup is blocked until all replacement surfaces are proven live:

1. `session-inbox` covers OpenCode session transport and `/sendoff` behavior.
2. Generated lifecycle/IAP message tools write valid, correctly named packets under `.agents/messages/`.
3. Generated lifecycle work-item tools operate on `.agents/{sdlc,rlc,mlc,wlc}`.
4. Generated OpenCode adapters load without import/path errors.
5. Generated tool visibility is agent-specific.
6. Old `~/.config/opencode/plugin/iap-sdlc*` sources are proven non-load-bearing for the tested behaviors.

Only after those conditions pass should local OpenCode plugin residue be deleted.

## Consequences

- Work-item cleanup is not an audit task. It is blocked by replacement implementation and live proof.
- `lifecycle-core` must support both message packet tools and lifecycle work-item tools.
- Existing broad references to `.agents/research`, `.agents/marketing`, or `.agents/writing` as lifecycle roots must be corrected or intentionally preserved as domain-specific state outside the lifecycle protocol.
- Existing broad work item key schemas may need tightening once the canonical work-item id regex is implemented.
- Harness-programming docs should teach these two filesystem protocol families explicitly.
