# Filesystem Protocol Family Authoring

This document defines the authored model for protocol families that persist structured artifacts to the repository filesystem.

It exists because lifecycle packets, lifecycle work items, and future signal queues share the same pressure: agents should not invent filenames, paths, envelopes, or persistence rules in prose. Those rules are protocol behavior and belong in canonical code.

## Definition

A filesystem protocol family is a reusable domain protocol that:

- owns one artifact root under the workspace, such as `.agents/messages/` or `.agents/sdlc/`
- owns the artifact representation, such as JSON packet or markdown work item
- owns typed identifiers, payload schemas, filename policy, and persistence rules
- exposes canonical tools that are the only supported mutation surface
- can be lowered into agent-specific synthetic tools for a target harness

A protocol family is not just a folder convention. The folder, filename, payload, and mutation rules form one contract.

## Current Families

### Lifecycle Message Packets

Root:

```text
.agents/messages/
```

Artifact:

- JSON packet
- shared IAP/lifecycle envelope
- family-specific `metadata.schema_id`
- contract-heavy `content.data`

Ownership:

- shared packet writer owns timestamp, filename, envelope, persistence, and receipt
- canonical message tools own semantic packet families such as `submit_work`, `submit_review`, `submit_self_assessment`, `submit_review_findings`, and `promote_pattern`
- generated synthetic wrappers validate the agent-specific contract before delegating to the canonical handle

Message filenames are part of the audit protocol. They must be generated by the tool/runtime.

### Lifecycle Work Items

Roots:

```text
.agents/sdlc/
.agents/rlc/
.agents/mlc/
.agents/wlc/
```

Artifact:

- markdown work item
- folder location is lifecycle state
- filename embeds the canonical work item id plus a readable slug

Ownership:

- lifecycle board helpers own create/list/read/update/transition/promote behavior
- canonical tools mutate by id, not by caller-authored path
- concrete lifecycle plugins grant root-specific synthetic tools to the orchestrator agent for that lifecycle

Lifecycle roots are method roots, not broad domain roots:

- `sdlc` = software development lifecycle
- `rlc` = research lifecycle
- `mlc` = marketing lifecycle
- `wlc` = writing lifecycle

Broad domain skills and folders such as `research`, `marketing`, and `writing` remain separate from lifecycle state.

Work item ids follow:

```text
<CODE>-<NNN>[subtask]
```

Where `CODE` is a two- or three-character uppercase project/workstream code, `NNN` is a three-digit sequence, and `subtask` is an optional lowercase letter. Example: `AP-039b`.

Work item filenames are generated as:

```text
<CODE>-<NNN>[subtask]-<title-slug>.md
```

Agents supply id, title, content, and target state. They do not supply filenames.

## Authoring Model

Protocol families are currently authored with existing compile primitives and ordinary TypeScript modules. They do not need a new first-class compiler primitive yet.

Use this shape:

```text
schemas/
  <family-types>.ts
tools/
  shared/
    <family-writer-or-board>.ts
  <semantic-tool>.tool.ts
tests/
  <family-behavior>.test.ts
```

The family should define:

- typed domain identifiers
- root and folder policy
- artifact schema or envelope
- payload schemas
- filename generation
- persistence/mutation functions
- canonical tool handles
- tests for accepted and rejected inputs

Traits or lifecycle `tool_grants` expose those canonical tools to agents. Lowerers generate synthetic wrappers and target-specific visibility, but wrappers do not own business logic.

## Boundary Rules

Canonical protocol families may use:

- pure TypeScript
- Effect Schema
- portable runtime context such as workspace root, agent name, timestamp, session id
- standard filesystem APIs

Canonical protocol families must not use:

- harness SDK imports
- TUI APIs
- session inbox transport
- hook callbacks
- runtime-only harness state that is unavailable across targets

If the capability needs those harness-native surfaces, make a standalone harness plugin project.

Examples:

- `lifecycle-core` owns lifecycle message and work-item protocol logic.
- `session-inbox` owns OpenCode session transport and `/sendoff` UX.

## Transaction Tools Are Different

Not every filesystem-writing tool is a protocol family.

Transaction-style tools such as `git_commit` perform one bounded operation against an existing system. They may need typed inputs and tests, but they do not define an owned artifact root, envelope, filename policy, or protocol-specific persistence model.

Use the protocol-family model only when the system owns a durable artifact family that future agents and tools will read, route, mutate, or audit.

## Future Signals

Future signal queues should follow the same model before implementation:

- choose the root
- choose whether the artifact is JSON, markdown, or another structured representation
- define signal ids and routing metadata
- define filename policy
- define append/read/consume mutation semantics
- expose mutations through canonical tools
- test the writer before exposing it through synthetic tools

Do not start with agent instructions like "write a file in this folder." Start with the family contract.

## Testing Requirements

Every filesystem protocol family needs tests for:

- valid artifact creation
- invalid id/root/folder rejection
- filename generation
- duplicate detection where applicable
- read/list behavior
- mutation behavior
- path traversal resistance
- returned receipt or summary shape

For generated harness surfaces, add at least one smoke proving the generated wrapper delegates to the canonical handle and writes the expected artifact under the expected root.

## Summary

The current canonical end state is:

```text
canonical protocol family
+ shared TypeScript writer/board
+ canonical tools
+ trait attachment or lifecycle tool grant
+ generated synthetic wrapper
= audited filesystem artifact
```

This gives agents narrow, typed mutation surfaces while keeping filenames, envelopes, and persistence policy in code.
